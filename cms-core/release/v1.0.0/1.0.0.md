## Overview

CMS Core Service manages institution and card-product configuration, card issuance and lifecycle, protected card data, HSM key assignments, and integration with the authorization switch and notification service. CMS owns card-management workflows; payment authorization decisions belong to the switch.

## Features

- **Institution and product configuration:** Institution onboarding and policies, card products and versions, issuance profiles, designs, BIN ranges, and product mappings.
- **Card issuance:** Durable issuance operations, virtual-first workflows, physical production requests, and operation-status retrieval.
- **Card lifecycle:** Activation, holds, hot-listing, renewal, replacement, and closure through guarded lifecycle commands.
- **Card controls:** Channel controls and transaction-limit changes, with accounting validation and Switch propagation where configured.
- **PIN operations:** Switch-owned initialization, change, and reset orchestration, encrypted request material, operation polling, and CMS audit history.
- **HSM keys and card security:** Institution-scoped key inventory, BIN key assignments, rollover handling, and envelope protection of sensitive card data.
- **Switch synchronization:** Durable HTTP outbox for card registration and lifecycle updates, authenticated transport, retry handling, and command receipts.
- **Notifications:** Transactional PostgreSQL outbox with authenticated HTTP delivery to `cms_notification`.
- **ACS contact lookup:** Restricted lookup of registered mobile/email by PAN. Contact synchronization from Accounting remains deferred; see limitations.

## Security

- Stateless JWT authentication with configured issuer, audience, permissions, and institution context protects V2 APIs.
- Legacy `/cms/api/v1` routes are denied. V1 consumers must migrate to the supported V2 contracts.
- Mutation idempotency and tenant context support safe retries; follow the mutation guide for endpoint-specific requirements.
- ACS lookup requires an allowlisted service-account subject, `platform_access: true`, and `cms:acs-contact:read`. An empty subject allowlist denies access. Responses do not echo the PAN and successful results use `Cache-Control: no-store`.
- Sensitive card data uses envelope encryption and HSM-backed key protection. Production keys, certificates, identity-provider grants, and secrets require environment-specific provisioning.

## Reliability and maintenance

- Durable lifecycle operations separate accepted requests from asynchronous execution and expose polling contracts.
- Outbox delivery uses leases, retries, bounded retention, and administrative replay controls.
- Expanded tests cover V2 controllers, lifecycle command boundaries, PIN workflows, HSM services, BIN rules, and Switch transport.
- The Maven coverage gate targets the configured V2 and supported shared-runtime scope. No measured performance improvement is claimed.

## Pre-release corrections

- Migrated the application baseline to Java 25 and Spring Boot 4.1.1 while retaining Jackson 2 APIs through the compatibility dependency.
- Denied legacy V1 routes and removed the insecure legacy encryption utility.
- Changed notification HTTP 409 handling to retry delivery rather than mark the event published.
- Local changes refine BIN uniqueness and PAN interval ownership, including historical ranges, and introduce database enforcement through migration 038.
- Removed obsolete replacement and local PIN execution paths in favor of lifecycle-command and Switch PIN ownership, as documented in the coverage guide.

These items describe the committed baseline and current local changes. The final release must select and verify the exact delivered snapshot.

## Deployment prerequisites

- Configure `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, and `DB_SCHEMA`; prepare the target schema and migration permissions.
- Review `db/changelog/db.changelog-v2.yaml`, the configured active changelog. Execute migrations in its explicit order; do not substitute the legacy master changelog.
- Migration 038 adds customer contact fields and a PostgreSQL GiST exclusion constraint for platform-wide PAN interval ownership. Resolve existing overlaps before applying it; closed ranges remain reserved. Rehearse this migration against a representative database copy.
- Configure `CMS_AUTH_ISSUER_URI`, `CMS_AUTH_JWK_SET_URI`, and `CMS_AUTH_AUDIENCE`, and provision the required service-account permissions.
- Provision HSM keys, certificates, trust settings, and institution/BIN assignments. Replace bundled development credentials and certificate settings through the approved secret/configuration mechanism.
- Configure Switch token credentials, recipient certificates, and transport security. The switch-sync profile is included by default; review its effective `SWITCH_BASE_URL` and TLS settings. TLS defaults to disabled in that profile.
- Configure notification authentication and destination, Accounting limits integration, and enabled vendor workflows.
- For ACS, configure `cms.security.acs.allowed-subjects` and arrange a supported contact-data population process before enabling client use.

## Known limitations

- **Candidate identity:** Current source includes uncommitted application and test changes. Final release identity and matching build evidence are not established.
- **ACS contact population:** Accounting contact transport/synchronization is deferred. Existing customers return 404 from lookup until contact data is populated; no public contact-write API is supplied.
- **Migration prerequisite:** Existing overlapping PAN intervals must be resolved before migration 038 can succeed.
- **PIN dependency:** PIN operations depend on the configured Switch recipient certificate, supported adapter/profile, permissions, and HSM integration. Confirm compatibility with the delivered Switch version.
- **Container port mismatch:** The supplied default application port and Docker health-check port differ; align them before deployment.
- **Verification scope:** Historical tests exclude the PostgreSQL outbox integration suite and include 51 skipped tests. Final candidate verification, live integration, migration/recovery rehearsal, performance, and UAT acceptance are not confirmed.

## Rollback

Before rollout, retain the exact previous application image, effective configuration, and a tested database recovery point. For first installation, agree the pre-install recovery state.

Stop new mutations and coordinate lifecycle, Switch-sync, PIN, and notification workers before recovery. Assess in-flight and uncertain external operations before restoring a compatible application/configuration. Application rollback does not reverse database migrations; restore or reverse schema/data changes only through the rehearsed recovery procedure. Reconcile external receipts and outbox state before resuming work, and avoid blindly replaying accepted operations.
