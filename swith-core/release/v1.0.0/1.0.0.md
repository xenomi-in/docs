## Overview

Switch Core 1.0.0 is the first client delivery of the issuer-side payment processing application. It provides RuPay transaction processing, card controls, prepaid withdrawal validation, NCMC service handling, and integration with card management, HSM, and accounting services.

This baseline includes the current local application and test changes. As this is the first delivery, the capabilities below describe the functionality supplied in version 1.0.0 rather than changes from a previously delivered client release. Visa, Mastercard, and debit card products are outside this delivery scope.

## Features

- **RuPay transaction processing:** Processes configured credit and prepaid ATM, purchase, and e-commerce transactions, including validation, authorization responses, duplicate checks, and reversals.
- **Card management integration:** Supports card registration, authorization profile updates, replacement-card transitions, and retrieval of command results. Retry and revision checks help prevent duplicate or outdated updates.
- **PIN services:** Provides customer-selected PIN initialization, change, and reset workflows through encrypted requests and configured HSM integration. Supported formats and activation prerequisites are listed below.
- **Standing instructions:** Includes standing instruction validation for the credit card product. Issuer-initiated mandate revocation is implemented but has the listener authentication limitation described below.
- **Operational visibility:** Supplies health checks, routing readiness, metrics, and notification integration for transaction operations.

## Security

- Service authentication and scope checks restrict access to payment and administrative interfaces.
- Encrypted card and PIN provisioning, AES-GCM cardholder-data protection, and HSM-backed key wrapping support protection of sensitive data.
- The production container runs as a non-root user. Production Compose restricts filesystem writes, drops Linux capabilities, and prevents privilege escalation.

## Reliability and maintenance

- **Consistent responses:** Centralized response handling maps transaction decisions to RuPay response codes, supporting consistent downstream interpretation.
- **Local card authorization data:** Card authorization uses profiles maintained within the switch, avoiding a synchronous CMS lookup during each authorization.
- **Integration efficiency:** Reuses HSM and outbound accounting connections, caches accounting access tokens, and caches frequently used reference and parsed transaction data. No measured throughput or latency improvement is claimed.
- **Automated verification:** Expanded tests cover transaction validation, card and PIN services, reversals, HSM communication, cryptography, and NCMC handling.

## Pre-release corrections

The initial delivery includes the following corrections:

- **Missing scheme rules:** Handles an unavailable rule list without an unexpected processing error.
- **E-commerce classification:** Distinguishes domestic transactions from cross-border transactions when applying international e-commerce checks.
- **Optional transaction data:** Handles missing or blank additional-data fields before attempting to parse international transaction indicators.
- **Java 25 compatibility:** Corrects card-data initialization for the Java 25 runtime.

Track-data extraction and iCVV service-code adjustments are included as integration changes below; production compatibility is not confirmed.

- The local Docker environment example now uses port `9701`; local listener service URL settings were updated.
- Mockito 5.23.0 is configured with a Java agent for Java 25 test execution. No successful final artifact packaging or container smoke-test result is asserted.

| Product scope | RuPay Credit and Prepaid, including NCMC under Prepaid |
| External dependencies | TCP Listener, HSM, Accounting API, identity provider; CMS and notification integrations where enabled |

Protected APIs require configured JWT identity and scopes; production switch API configuration requires mutual TLS. Existing unauthenticated consumers must supply the required tokens and certificates. Compatibility with an existing client integration is **Not confirmed**.

The following interfaces form part of the initial API baseline:

| Interface | Purpose |
| --- | --- |
| POST /api/v1/iso8583/transaction | Submit an ISO 8583 transaction for processing |
| GET /api/v1/iso8583/health/routing | Check readiness to route transactions |
| POST /api/v1/issuer-mandates/revocations | Request issuer-side mandate revocation |
| /internal/v1/institutions/{institutionId} | Base path for CMS card registration, authorization profiles, card transitions, command receipts, and PIN operations |

- **Authentication requirements:** Transaction calls require a service JWT with the configured issuer, audience, client identity, and `switch:transaction:write` scope. Status, mandate, and CMS interfaces require their respective scopes. Production configuration requires mutual TLS for switch APIs.
- **CMS request contract:** Mutation calls use idempotency keys and revision checks. Card provisioning and PIN material use encrypted envelopes. Consult the supplied CMS API documentation for payloads and error responses.
- **HSM compatibility:** The local iCVV service-code setting is `620`, changed from `999`. Track 2 security-code extraction also uses an updated issuer-specific position. Validate both against the intended card profile and HSM before enabling the corresponding flows.
- **Compatibility:** Unauthenticated clients and clients without the required scopes or certificates cannot use protected interfaces. API compatibility with any existing client integration is **Not confirmed**.

## Deployment prerequisites

The supplied Liquibase changelog references migration scripts V1–V15 for NCMC services, merchant rules, standing instructions, card/account fields, prepaid balance snapshots, CMS authorization mappings, encrypted card data, and PIN operations.

- Review the existing schema and migration dependencies before execution. The changelog starts with V10 before V1–V9; script filenames must not be used to infer execution order.
- The production example validates the schema and disables automatic Liquibase execution by default. Apply the reviewed migration plan before application startup.
- No additional schema migration was identified among the latest local changes.

| Configuration | Required setup |
| --- | --- |
| SERVER_PORT | Default application port is 9701; listener URLs must match |
| SWITCH_SITE_ID / SWITCH_NODE_ID | Set deployment identities; node identities must be unique within a site |
| SWITCH_API_JWT_ISSUER / SWITCH_API_JWT_JWKS_URI | Configure the trusted token issuer and public-key endpoint |
| CMS_SWITCH_TLS_ENABLED | Enable with certificates for secure CMS integration; local profile defaults to false |
| CMS_PIN_HSM_ENABLED | Enable only after target HSM validation; default is false |
| prepaid-limits.* | Review withdrawal enablement, count, time window, and time-zone settings |

Provision database access, HSM keys and certificates, Accounting API settings, and RuPay credit/prepaid BIN and reference data through the deployment configuration. Do not distribute live credentials with source code.

- Confirm the target environment and delivery date, and provide the required database, identity-provider, network, certificate, and HSM integration settings.
- Configure RuPay credit/prepaid products, BINs, NCMC services, transaction permissions, and approved withdrawal limits.
- Update API consumers to use the required JWT scopes, certificates, encrypted payloads, and retry/version contracts.
- Agree the target card and HSM profile before validating iCVV, Track 2, and PIN operations.
- Complete environment-specific integration and migration testing, including the database scenarios skipped in vendor verification.
- Resolve the sensitive HSM logging condition with the vendor before production deployment. Use a single-instance prepaid-limit deployment unless multi-instance enforcement has been validated.

## Build and deployment

Build the final selected source in a clean release checkout using `mvn clean verify`. The available verification covers `mvn clean test`; packaging and verify-phase results are **Not confirmed**. The Dockerfile skips tests during packaging.

For a version-labeled image, use `docker build -t switch-core:1.0.0 .`. Record the final release commit, packaged artifact SHA-256, image digest, and evidence from the same verified build. These identities are **Not confirmed** for this candidate.

Configure `APP_IMAGE` and the target runtime settings, then deploy with `docker compose --env-file .env.prod -f docker-compose.prod.yml up -d`. Review the production deployment guide and provision certificates and configuration before startup. Replace supplied test certificate material with environment-specific certificates.

## Known limitations

- **Listener authentication:** The current outbound mandate-revocation gateway does not attach a bearer token. It is incompatible with the protected TCP Listener API as implemented; direct mutual TLS may also reject calls without a client certificate. This for the txns orginate from the switch i.e SI mandatorry call for deregistration . will be fixed in next release
- **Sensitive diagnostic logging:** The delivered local HSM client logs complete outbound commands at INFO level. This path is not controlled by the normal raw-payload flag. This temp enabled for dubug purpose.

- **Prepaid concurrency:** Withdrawal-limit validation uses single-instance synchronization. Consistent enforcement across multiple active application instances is **Not confirmed**.
- **PIN support:** The documented execution adapter supports ISO_0 blocks and VISA_PVV with an explicit PVKI. IBM offsets, ISO_4 execution, TR-31 input keys, and generated PIN/mailer execution are unsupported by that adapter.

- **Production readiness:** Live integrations, migration/recovery rehearsal, production performance, and applicable certification are **Not confirmed**.

## Rollback

No earlier client deployment is confirmed. For a first installation, stop the new instance and restore the agreed pre-install state if withdrawal is required. If replacing an actual unversioned deployment, retain that exact image, configuration, and database recovery point before rollout.

Stop new routing through the agreed operational procedure, assess in-flight transactions and reversals, and restore the retained compatible application/configuration. Restore or reverse database changes only through a tested recovery procedure; application rollback does not reverse schema changes. Reconcile transactions before resuming traffic and do not blindly replay requests.
